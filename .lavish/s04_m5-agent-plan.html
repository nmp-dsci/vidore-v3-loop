1 · your six points

Short answers, with the detail further down

Can the judge be Sonnet or Haiku? Haiku first

Haiku 5.5 re-judges M4's 310 train verdicts first, and it should be close: the judge reads about 1.8k tokens and picks one of three labels. We adopt it if it matches Opus; Sonnet 5.5 is tried only if Haiku misses. Step S1.

Answer agent: Haiku first Haiku 5.5

Haiku 5.5 runs alone first, since its job is to read the pages that search finds. We compare it with the board on train, and move to Sonnet 5.5 only on a large gap: more than the ±3.8 points 155 questions can resolve. The ladder.

Latest model versions always latest

The code stops pinning versions; today two of the pins are stale. Step S0 passes the alias (haiku, sonnet, opus, fable) straight to the Agent SDK, which resolves it to the newest model. Each run records the exact id it got. Models.

Why not score all 309? we will

The board's numbers cover all 309, and pooling M4's two runs already gives 67.6% and 72.9. The rule limits what we choose on, not what we score: choices are made on train, so test stays a clean check once M6 tunes prompts there. Scoring.

Effort high, for judge and agent

Haiku 5.5 runs at high effort as both the judge and the answer agent, set explicitly because its default is medium. Sonnet 5.5, if it's needed, also runs at high, so the step up changes only the model. The ladder.

Keep the work on this branch yes

All M5 commits go to ft-vllm-embed. Nothing goes to main until you say. The branch holds only the s03 plan so far.

Why the pipeline gets only the top 5

Top 5 is the paper's method. Every retrieved-pages row in its Table 3 (ColEmbed-3B-v2, hybrid, jina-v4 + zerank-2) hands the generator the top 5 pages, so M4 does too (answer/generate.py, K = 5). That keeps our pipeline row comparable with theirs.

The agent isn't held to 5

The agent chooses what to read: up to 5 searches and up to 10 page views per question. That makes it a different kind of system from the paper's rows, much as NeMo's agent is on the retrieval board. Its row is labelled "agent", and the M4 pipeline row sits beside it as the like-for-like comparison.

Where the points go today (all 309). 194 questions are right both ways. 36 are wrong from our top 5 but right from the human pages; the agent goes after these. 15 are right only from our top 5. 64 are wrong even with the human pages. Those come down to how the answer is written, the judge, or a wrong reference: 2 of the 5 hand checks found a wrong reference. The 40-label check on the Review tab measures that part.

3 · all 309 vs train

Score all 309; choose on the 155

What changes

  • Every configuration that reaches test is also run on train, so its all-309 figure is a weighted mean of the two runs. No question is scored twice.
  • The Leaderboard tab shows both columns: all 309 to compare with the board, and test 154 as the clean check.
  • The test guard stays: a test run needs --final, and a configuration already scored on test is refused.

Why train still matters

  • The all-309 figure includes test, so choosing a model, an effort or a prompt by looking at it would be choosing on test.
  • After M6 tunes prompts on train, the all-309 figure flatters us by however much train overfits. The test figure shows the gap.
  • Train runs 1.8 points above all 309 on NDCG@10 and 1.8 points below on answers (M4). The ladder's bar takes this into account.

5 · the judge

Haiku 5.5 first, checked against Opus before switching

The judge is the ruler for every number in M5, so it's fixed before the ladder runs. The prompt stays the paper's (Figure 24), and only "Correct" counts.

Re-judge train with HaikuTake M4's 310 train verdicts: 155 questions, each with a top-5 answer and a human-page answer. Judge them again with Haiku 5.5, plus a second Opus 5.5 pass that shows how often Opus disagrees with itself. Haiku runs at high effort; the Opus pass stays at medium, as M4 ran it. The answers aren't regenerated.
CompareHaiku's yes/no agreement with Opus's first pass, Cohen's κ, and how far its accuracy moves (lenient or strict). It's also checked against your 40 labels if they exist.
RuleAdopt Haiku if it agrees with Opus on at least 95% of the Correct / not-Correct labels and moves accuracy by 1 point or less. If Opus agrees with itself on fewer than 95%, Opus's own figure is the bar. Against your 40 labels, Haiku must also be at least as accurate as Opus. If Haiku misses, Sonnet 5.5 runs the same check. If both miss, Opus stays.
Re-score M4If the judge changes, M4's runs are re-judged so every row sits on one judge. The old verdicts stay in their run folders.

Why Haiku should be close, and where it might not be

The task is small: a question, a reference and an answer, then one of three labels. That suits Haiku. The risk is the line between Correct and Partially Correct. In M4, 68 of 309 top-5 answers were Partially Correct, and only Correct counts, so a slightly more lenient judge moves the score by points. The check measures exactly that line.

A judge may also favour answers from its own model family, and Haiku will judge Haiku's answers at rung R1. At the end, Opus re-judges 50 of the agent's train answers. If agreement drops, the judge reverts to Opus.

6 · the agent

Search, read, then one structured reply

The agent is one Agent SDK session per question, billed to the subscription and sealed like M4's: no built-in tools, no settings files, an allow-listed environment. Two in-process tools are its only way out. The installed SDK (0.2.165) passes images back from in-process tools.

PieceWhat it doesWhy
search(query)The champion ranking (EVIE-4.5B, visual only, the same pipeline.compute() runs use). Returns 10 results: page id, document, page number and the page's first 300 characters of text. At most 5 calls.The agent's search is the system we already scored, so the agent's gain is measured against it alone. The cap is s00's.
view_page(id)The page image plus its OCR markdown, exactly as M4 gives them. At most 10 pages a question.M4 measured about 4.4k tokens a page. Ten pages keep a question under about 50k tokens of context.
final replyStructured output: {ranking: 10 page ids, answer, cited}. The answer follows the paper's line, "Keep the response short when appropriate. Output the answer only."The 5.5 models reject forced tool use, so the final reply uses structured output, as the judge already does. Keeping the paper's wording keeps answers comparable with Table 3.
short rankingFilled from RRF over every search the agent made.NeMo's fallback, so NDCG@10 always scores 10 pages.
no think tools00 listed one; M5 drops it.The 5.5 models think between tool calls on their own.

What a run stores, and the Agent tab that reads it

runs/<id>/run.json plus agent.jsonl, one line per question with:

  • every step: the tool, its input, the page ids returned, milliseconds
  • the final ranking, answer and cited pages
  • the verdict and the explanation
  • tokens and API-equivalent cost

The fingerprint covers the model, the effort, the judge, the caps, the prompt hash, the tool-schema hash and the retrieval config. Runs are resumable and immutable once scored, and each one logs to MLflow (vidore-v3-loop/evals, with the required tags).

Agent tab, at /agent/v1?run=<run>&query=<id> (s00's URL grammar), shows one question's steps in order. A sketch, not a real trace:

7 · the ladder

Haiku 5.5 first; move up only on a large gap to the board

The answer bar on train is 65.5%: the paper's 67.3%, moved down by M4's 1.8-point gap between train and all 309. NDCG@10 is compared with the board (75.9, or 77.7 on train) on every rung. A rung that ranks worse than its own search tool (74.7 on train) points to a bug, not a weak model.

8 · build order

Seven steps, each ending in something to open

S0 · aliases, not idsRemove the pinned ids from MODELS and pass aliases to the SDK. Add the start-of-run resolve, vidoreloop models, and the test that rejects a hardcoded id. Make one smoke call per alias on the subscription.
S1 · judge checkAdd vidoreloop rejudge <run> --judge <model>: an earlier run's answers, judged again, never re-answered. Check Haiku 5.5 first, and Sonnet 5.5 only if Haiku misses (section 5's rule, on train). You label 40 judged answers on the Review tab while it runs.
S2 · pipeline baselineRun M4's pipeline on train with Haiku 5.5 at high effort, with retrieved and human pages, on the chosen judge. This gives the latest-model row and the baseline for Haiku's agentic gain. Sonnet 5.5's baseline runs only if rung R2 does.
S3 · build the agentAdd answer/agent.py (the tools, caps, final schema and fallback fill), an agent call in answer/claude.py that records each step, and eval/agents.py (runs, fingerprint, test guard, metrics, judge, MLflow). Then vidoreloop agent, the API routes, the Agent tab, and Leaderboard rows with all-309 and test-154 columns. Tests stay offline, using a fake SDK stream.
S4 · smokeRun 10 train questions on Haiku 5.5. Measure tokens, time and cost, then replace this page's estimates.
S5 · the ladderRun R1 (Haiku 5.5, high) on train, and R2 (Sonnet 5.5, high) only on a large gap. If Sonnet trails too, stop and review with you. Opus spot-checks 50 of the agent's answers to confirm the judge.
S6 · test onceRun the chosen agent and its same-model pipeline on test with --final. Publish both the all-309 and test-154 figures on the Leaderboard. Update README and AGENTS, and mark M5 done after your review.

How the agent estimate is made: about 8–12 turns per question, ≤ 5 searches of about 1k tokens each and ≤ 10 page views of about 4.4k each (measured in M4: 22.9k tokens for 5 pages). Context reaches 25–50k, and 150–300k tokens are read in total, mostly from the prompt cache. For scale, NeMo's agent used about 760k input tokens and 136 s a question with Opus 4.5. Heavy rungs may run into a subscription usage window; the code already waits for the reset rather than failing.

What could go wrong

IDRiskWhat we do
