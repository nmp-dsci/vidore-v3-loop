How EVIE finds the page

EVIE turns every page image into about a thousand small vectors and every question into a few dozen, then scores a page by how well each question piece finds its best match on the page. This page walks through where the model came from, how we indexed the 2,942 finance pages once, and what happens in the 2.5 seconds after a question arrives.

1 · the idea

One vector per patch, not one per page

Most embedders squeeze a page into one point. EVIE is a late-interaction (ColBERT-style) model: it keeps a vector for every 32×32-pixel patch of the page and every token of the question, and compares them only at search time.

2 · what came from Hugging Face

A 4.5B model, a library to run it, and the pinned dataset

We trained nothing. Everything below was downloaded and used as published.

The model · tencent/EVIE-4.5B

  • 8.5 GB of weights, Apache-2.0, snapshot 498388f
  • Built on Qwen3.5-4B: a vision encoder plus a language model
  • A 2,048-wide output head, then normalise, then keep every token
  • A template: pages get “Describe the image.”, questions get 10 padding tokens

How Tencent made it (from its card)

  • An 8B teacher (EVIE-8B, on Qwen3.5-9B) trained first
  • The 4.5B student distilled from it (their “ARD” recipe)
  • One head trained so its first 64…2,048 numbers each work alone
  • ViDoRe V3 mean 66.0; finance_en 70.0 in their protocol, 72.3 on MTEB's English board

The runner · sentence-transformers 6.1

  • MultiVectorEncoder loads the model's four modules
  • encode_document for pages, encode_query for questions
  • transformers 5.17 and torch 2.14 on the Mac's GPU (MPS), bfloat16

The data · vidore/vidore_v3_finance_en

  • Pinned at revision 7f432c1
  • 2,942 page images from 6 financial reports, with OCR text
  • 309 English questions and their graded gold pages
3 · applying it to the dataset (once)

Indexing 2,942 pages took 11.2 hours on this Mac

The index was built over several nights between 1 and 8 October with make index-visual-overnight DATASET=finance_en, which calls visual.build.

Take the pages in corpus-id order, 50 at a timeEach batch of 50 becomes one file, part_00000.npz … part_02900.npz (59 parts), so a stopped run loses at most one part and a rerun skips finished parts.
Encode two images at a timeencode_document returns 1,019 × 2,048 per page; _cut keeps the first 128 numbers, renormalises and stores float16.
Save ids, lengths and vectorsEach part holds the page ids, how many vectors each page has (always 1,019 here, since every page has the same shape) and the vectors themselves; stats.json keeps the totals.
Stop cleanly if memory runs lowBelow 15% free memory the build stops at a part boundary; the same command resumes it.

7 · things worth knowing

Six details that matter for any change

The model isn't pinnedvisual.MODELS names no revision; our snapshot is 498388f, MTEB's file lists 8aecfa9Datasets are pinned, the model is not; a re-download could change the index
We keep 128 of 2,048 numbersThe card: V3 65.3 at 128 vs 66.0 at 2,048Wider vectors may add under a point, but the index stored only 128, so any change means re-encoding (11 h here)
